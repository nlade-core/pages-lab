actions latency

If something on this site updates itself automatically — no visitor involved, just time passing — how long does it actually take from "the update happened" to "you can see it"? Why bother: it's the real cost of not having a live server behind this.

Technical version

A scheduled GitHub Action commits a fresh timestamp every 30 minutes. Rather than fabricate a number, this pulls two of GitHub's own public, unauthenticated APIs live: commit history for the timestamp file, and the run history of GitHub's own pages-build-deployment workflow (the actual thing that rebuilds and deploys this site), correlated by commit SHA. The obvious pages/builds endpoint turned out to require auth even on a public repo — this works around that using the deployment workflow's own public run history instead.

Write-up

Two separate delays stack here, not one. First: GitHub explicitly documents that scheduled workflows aren't guaranteed to fire exactly on time — a 30-minute cron can slip by minutes during high load, so "how often" and "how promptly" are different, both-honest numbers. Second: once the commit lands, GitHub Pages still has to actually rebuild and deploy, which the history table above measures directly and separately from the first delay.

The commit timestamp already reflects whatever time the Action itself spent running before it pushed, so there's no need to separately measure the workflow's own execution time on top of this — it's already baked into when the commit landed.

The unauthenticated GitHub API is rate-limited to 60 requests/hour per IP — a real limit, unlikely to matter for occasional use here, but worth knowing if you refresh this a lot.
