pyodide

Can a browser tab run the same number-crunching tools you'd normally need a Python server for — and how much can it actually chew through before it's too slow to bother? Why bother: it's the difference between needing a backend for anything data-heavy, or not.

Technical version

Loads Pyodide (CPython + numpy compiled to WebAssembly) directly in-browser, no server involved. Times the real boot cost (runtime + numpy fetch and init), then runs an escalating numpy matrix-multiply benchmark against a plain-JS equivalent, stopping once a round crosses a slowness threshold. Matters beyond this lab: this is the same mechanism behind in-browser data-science tools like JupyterLite — the tradeoff is always this one, real download weight and WASM overhead versus not needing a backend at all.

Boot cost

Real download, timed live — nothing here is precomputed. Roughly 11.5MB for the core runtime, another 2.9MB for numpy, measured directly from the CDN.

Finding the ceiling

Runs increasing matrix-multiply sizes through numpy, timing each one, stopping once a round crosses 2 seconds. Sizes up to 256×256 also get a plain-JS comparison — bigger than that and a naive JS loop would freeze the tab, so it's numpy-only from there.

Write-up

The boot cost is real and up front — roughly 14.5MB has to land before any Python runs at all, which is a genuine cost on a slow connection or mobile data, not a rounding error. It's a one-time cost per browser cache, though: the CDN serves these files with a one-year cache lifetime, so a repeat visit skips the download entirely.

Once loaded, everything runs on the main thread — there's no Web Worker here, which means a big enough computation genuinely freezes the tab's UI while it runs, not just "feels slow." That's part of what the benchmark is actually measuring: not just numpy's raw speed, but the point past which making the visitor wait becomes a bad trade.

The numbers speak for themselves rather than a claimed multiplier — run it and compare the two columns directly.
