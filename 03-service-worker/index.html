service worker

If you visit this page once and then lose your connection — flight mode, dead signal, wherever — does it still show you something, or just the browser's blank error? Why bother: this is literally how offline-capable web apps work.

Technical version

Registers a service worker scoped to this experiment's own directory. On install it precaches this page; on every later request within scope, its fetch handler serves cache-first, falling back to network. Matters beyond this lab: any "installable" PWA (Twitter Lite and most offline-capable web apps) runs on this exact mechanism — and the classic "why isn't my update showing up" bug comes from this same cache not being invalidated properly, which the versioned cache name here is the standard fix for.

Test it for real

First, check the box above: "service worker" should say active and the cache list shouldn't be empty. That's this visit having actually cached the page — nothing below proves anything until that's true.

  1. Open your browser's DevTools (Cmd+Option+I on Mac, Ctrl+Shift+I on Windows/Linux) and go to the Network tab.
  2. Check the Offline box. This cuts network access for this tab only — no need to touch your actual wifi.
  3. Make sure "Disable cache", usually right next to it, is unchecked. That one specifically defeats what's being tested here — a common false negative.
  4. Reload normally (Cmd+R / Ctrl+R). Not a hard refresh (Cmd+Shift+R) — browsers deliberately let a hard refresh skip the service worker, so that would make a working cache look broken.

If the page still loads with Offline checked, that's the real mechanism working: GitHub Pages never saw this request, your browser served it from what it saved on an earlier visit. Uncheck Offline afterward to go back to normal. No DevTools handy? Airplane mode plus a normal reload proves the same thing, it just cuts your whole connection instead of one tab's.

Write-up

The first visit has to be online — nothing gets cached until it's fetched at least once, so "works offline" only kicks in after that first successful load. The service worker is also scoped to this one directory: it doesn't make the rest of pages-lab, or the internet generally, work offline, only the files explicitly listed for precaching here.

The well-known gotcha: without a versioned cache name and cleanup on activate, a service worker will happily keep serving an old cached version forever, even after a real fix has shipped — that's the "why won't my update show up" bug every service worker tutorial eventually warns about. The cleanup here (old cache names get deleted on activate) is the standard mitigation, not a guarantee — bump the version string in sw.js and the old cache is swept on the next activation. This isn't hypothetical: it happened live while building this page — an earlier visit had cached a version before a feature existed, and even after the fix deployed, it took a second reload before the update actually took over. First reload only tells the browser sw.js changed; the new version installs in the background but the page you're looking at is still controlled by the old one. Second reload is the one that actually hands control to the new version.

Requires HTTPS (or localhost for local testing) — GitHub Pages serves over HTTPS by default, so that's a non-issue here, but it's worth knowing this silently doesn't work over plain HTTP.
